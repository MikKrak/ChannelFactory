# Правила проекта ChannelFactory

## 1. Источник истины и инструменты

Каноническая память проекта — GitHub `MikKrak/ChannelFactory`. Для чтения и изменения репозитория используем **подключённый GitHub-плагин напрямую**; переход в Work для обычных операций с GitHub **не требуется**. Чаты ChatGPT — исполнители ролей, а не единственное место хранения решений. Локальная рабочая папка Mac и GitHub не синхронизируются автоматически.

Перед работой читать `INDEX.md`, `AGENTS.md`, `STATUS.md` и относящиеся к задаче документы.

## 2. Решения и полномочия

Различать подтверждённые факты, согласованные решения, гипотезы, предложения и открытые вопросы. Новые организационные или продуктовые решения не становятся каноническими без согласования владельца. Существенные изменения структуры, кода, развёртывания и секретов предварительно согласовывать. Утверждённое задание выполняется в оговорённых границах без повторного запроса разрешения на каждый файл.

При записи проверять актуальную версию файла и избегать перезаписи чужих изменений; сообщать путь, ссылку и commit SHA. Не создавать параллельные канонические копии.

## 3. Две независимые структуры

**Предметная:** концепция продукта → техническая архитектура → программная реализация и проверенные результаты.

**Рабочая:** управление проектом → специализированные чаты → задания и результаты. Организация чатов не определяет структуру программных модулей, а программная структура не диктует количество чатов.

## 4. Вертикальный обмен

Вниз передаются решения, приоритеты и задания; вверх — результаты, фактическое состояние, проблемы и предложения. См. `управление/иерархический-обмен.md`. Соседние чаты не ставят друг другу обязательных задач в обход общего управляющего. Чат не может автоматически активировать другой чат: владелец запускает работу вручную.

## 5. Документы, план и состояние

`концепция/CONCEPT.md` — текущая каноническая концепция; `STATUS.md` — только проверенное состояние; `разработка/DEVELOPMENT.md` — исследования и технические заметки; `reference/PLAN.md` — исторический план; `разработка/WORK_PLAN.md` — текущий технический план. `управление/план-проекта.md` служит организационной картой и ссылается на подробные планы, не дублируя их.

Не создавать пустые каталоги и фиктивные задания. Не объявлять план реализованным до проверки.

## 6. Код и безопасность

Согласованное имя будущего каталога программы — `CF-application/`; целевой Root Directory в Vercel — `CF-application`. Перенос кода с Mac, настройка Vercel и изменение работающего приложения — отдельные этапы после проверки и резервного копирования.

Никогда не сохранять в GitHub `.env`, токены, ключи, пароли, виртуальные окружения и прочие секреты. Перед публикацией исходников проверять состав изменений. Сохранять возможность локального запуска и учитывать ограничения Vercel Hobby.

При расхождении с `AGENTS.md` или текущим состоянием не угадывать: сообщить о противоречии и предложить согласование.

## 7. Язык рабочих документов

Писать простым, точным русским языком, как в разговоре между людьми, которые вместе делают программу. Это относится к заданиям, отчётам, планам, предложениям и решениям.

- Называть конкретное действие и результат: что сделать, как проверить, кто решает.
- Не использовать канцелярские, научно-подобные и абстрактные выражения там, где можно сказать проще.
- Технические термины использовать по делу и при первом упоминании коротко объяснять, если смысл неочевиден.
- Не заменять ясность красивой формулировкой: читатель не должен догадываться, что стоит за словами.
- Писать понятными предложениями, без торжественного тона. Краткость не должна вытеснять полноту: указывать нужные для понимания предмет, участников, действие, результат, ограничения и место фиксации решения — там, где это важно. Не упрощать содержание и не скрывать важные ограничения.

Пример: вместо «независимое состояние доставки для каждой точки присутствия» — «для каждого канала отдельно записывать, удалось ли опубликовать пост».

Не оставлять неопределённых слов вроде «правила», «механизм», «обеспечение», «взаимодействие» без нужной конкретики. Например, вместо «Какие правила нужны перед регулярной работой?» — «Нужно определить, из каких источников редактор может брать материалы, на каких условиях их публиковать и какие сведения о читателях программа вправе сохранять. Принятые требования записать в документах проекта». Это не исчерпывающий перечень требований, а пример нужной точности.

**Проверка текста:** после чтения должно быть понятно, что именно предлагается, кому это нужно, что предстоит сделать или решить и где будет зафиксирован результат. Если ответ зависит от контекста, его следует указать; не обязательно расписывать очевидное.
