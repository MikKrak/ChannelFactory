# CF-02C-007: ограниченный приём обращения

Модуль incoming.py не подключён к FastAPI, при импорте ничего не запускает.
Рабочая Supabase, публикации, зависимости и .env не меняются.

## Перед первым реальным вызовом

Получить согласование владельца: нет другого потребителя, какой обычный аккаунт
пишет каналу, несекретный текст, время опыта, место/срок локального хранения.
Пустой webhook не доказывает отсутствие внешнего polling. Локальный flock
защищает только экземпляры, использующие тот же каталог; 409 останавливает опыт,
но отсутствие 409 тоже не доказывает единственность потребителя.

Предлагаемое место: /private/tmp/cf-incoming-007-20261030/ (каталог 700,
events.sqlite3 и receiver.lock 600). Вне Git. Срок: до приёмки, максимум 24 часа
после опыта; затем отдельно согласовать удаление или перенос. Временный каталог
может быть очищен системой — это не постоянное хранилище обращений.

Один capture_once: проверка getMe/getWebhookInfo/getChat → один getUpdates
с timeout=0, limit=100 → атомарное сохранение всего пакета → остановка.
offset и allowed_updates не передаются. Действует прежний фильтр Telegram;
его неизвестное состояние — ограничение, отсутствие события не доказывает
невозможность приёма. Фильтр этим опытом не меняется. Нет отрицательного offset,
drop_pending_updates, setWebhook/deleteWebhook, sendMessage и повторов сети.

Очередь остаётся неподтверждённой даже после сохранения. Следующий запрос с
offset требует нового решения, поскольку подтвердит ВСЕ меньшие update_id.
Если получены посторонние события, они сохраняются приватно и не подтверждаются.
Если пакет из 100 старых событий не содержит тестового, остановиться и согласовать
дальнейшие действия; не обходить очередь автоматически. В stdout только количества,
без текстов, имён, токена и полных событий. SQLite соединение и lock закрываются.

## Нормализация

Проверяются update.message, известный chat.id, is_direct_messages=true,
direct_messages_topic.topic_id, обычный отправитель, текст, message_id/date.
Маршрут будущего ответа — chat_id служебного DM-чата и
direct_messages_topic_id из события. message_thread_id не подставляется.
Привязка к каналу задаётся проверенной конфигурацией, а не выдумывается из события.
Неизвестные/отредактированные события сохраняются как unsupported для следующего
этапа, не считаются обработанным текстовым обращением.

## Проверки

Из CF-application:

    .venv/bin/python -m unittest discover -s tests -p test_incoming.py -v

Все примеры синтетические. Полные реальные события в репозиторий не добавлять.

## Предложение следующего хранения (не миграция)

- События: bot_id/update_id — уникальный ключ; тип, время получения, состояние
  обработки и минимальный payload; доступ только серверу, срок хранения определить.
- Диалоги: проект/бот/канал, chat_id/direct_messages_topic_id — адрес переписки.
- Сообщения: диалог, message_id, направление, время, текст и ссылка на событие;
  уникальность входящего сообщения по боту/чату/message_id.
- Попытки ответа: сообщение, версия текста, состояние, receipt Telegram;
  неизвестный результат требует сверки, без слепого повтора.
- Курсор: bot_id, подтверждённый диапазон, lease/token единственного обработчика.
  Сначала транзакционно сохранить ВСЕ события пакета, затем разрешать offset.
  При сбое повторное получение безопасно благодаря уникальному ключу.

Нужны отдельная приёмка транспорта, схема и изолированные SQL-проверки;
в рабочую базу этим заданием ничего не добавлять.
