# Подключение журнала публикаций

Это локальная реализация по прямому поручению владельца после приёмки CF-02C-006.
Рабочая Supabase этим кодом автоматически не мигрируется. При запуске приложения
DDL не выполняется. Файл publication.sql содержит транзакционный SQL-скрипт;
он не зарегистрирован как применённая миграция Supabase.

## Перед применением к рабочей базе

1. Сохранить контрольный коммит кабинета и публикации; синхронизация — владельцем.
2. Отдельно согласовать целевую БД, резервное сохранение текущей схемы и SQL.
3. Остановить прежние экземпляры приложения. Обновление файлов на диске не меняет
   код, уже загруженный старым сервером; его прямой отправитель обходит журнал.
4. Оставить отправку выключенной. Проверить SQL на изолированной PostgreSQL,
   затем применить к согласованной цели одной транзакцией. Частичная установка
   таблиц без всех функций и триггеров недопустима.
5. Проверить права, RLS, список RPC и что редактор по-прежнему сохраняет draft/ready.
6. Выбрать новый тестовый пост и явно сверить канал. Прежний статус ready/draft
   не доказывает, что пост никогда не отправляли.

## Разрешение реальной отправки

Без обоих параметров сервер отказывает до обращения к Telegram:

- CF_PUBLICATION_ENABLED=1
- CF_PUBLICATION_ALLOWED_POST_IDS — список разрешённых UUID постов через запятую.

Значения конфигурации не записываются в код и не передаются браузеру. В .env
этой разработкой ничего не добавлялось. Параметры включает владелец только для
согласованного опыта. На странице подтверждения отдельно проверяются пост,
канал, редакция и отсутствие прежней отправки.

Старые URL /post/{id}/publish и /post/{id}/publish-now используют общий сервис
с новым кабинетом. Старая форма без revision отклоняется. Прямой вызов прежней
publish_to_telegram заблокирован. Это не способ заблокировать ещё работающие
процессы со старым кодом — их необходимо остановить до испытания.

## Проверки

Из CF-application, без сети и рабочей БД:

    .venv/bin/python -m unittest discover -s tests -v

SQL-тесты включаются только с CF_TEST_POSTGRES=1. Они обращаются исключительно
через socket /private/tmp:55439 к cf_publication_test и проверяют data_directory
/private/tmp/cf-publication-pg-20261029 до очистки синтетической схемы. Сама
fixtures/publication_base.sql также содержит этот запрет. SUPABASE_URL не используется.

Для воспроизведения нужен отдельный initdb-кластер PostgreSQL и psql. В кластере
создать роли anon/authenticated (NOLOGIN), service_role (NOLOGIN BYPASSRLS) и
пустую БД cf_publication_test. Сервер запускать с listen_addresses='' и socket
/private/tmp на порту 55439. Не использовать работающий общий кластер. Затем:

    CF_TEST_POSTGRES=1 .venv/bin/python -m unittest discover -s tests -v

Тесты сами загружают синтетическую структуру и publication.sql. На момент
разработки прошли на PostgreSQL 16.15; рабочий проект Supabase — PostgreSQL 17.
Применение и проверка на рабочем проекте остаются отдельным этапом.

## Неопределённость и ручная сверка

Успешные ответы записываются по одному. Тайм-аут, частичный успех и сбой записи
останавливают отправку. Даже после перезапуска и истечения review_after
запрещено автоматически повторять запросы Telegram или подхватывать pending.
Проверка зависания — POST-действие без сетевой отправки.

Перед ручной сверкой остановить/дождаться прежнего worker: checkbox фиксирует
заявление владельца, а не технически доказывает отсутствие процесса. Записать
основание, проверив канал. Можно дозаписать найденный receipt; решение хранится
в review_log. Завершение возможно лишь после подтверждения всех частей.
Закрытие без доставки возможно только после явной проверки и без confirmed
частей; затем нужен возврат в draft и новое утверждение. Частично доставленный
пост не разблокируется для автоматической повторной публикации.

## Возврат

Выключить отправку и перезапустить новый сервер, сохранив чтение журнала.
После реальных доставок не возвращаться к старому прямому отправителю и не
удалять receipts: это снова создаст возможность дублей. Откат кода не удаляет
сообщения Telegram. Автоматического удаления схемы или данных не предусмотрено.

Приём обращений, polling/webhook, ИИ-ответы и публичная защита редактора здесь
не реализуются. Приложение остаётся локальным однопользовательским прототипом.
