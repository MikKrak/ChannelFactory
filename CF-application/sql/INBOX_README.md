# Подключение обращений и ручного ответа

Локальная реализация по прямому поручению владельца после CF-02C-007.
**inbox.sql в рабочую Supabase не применялся.** Это SQL-скрипт, не запись
зарегистрированной миграции. Все испытания используют синтетические данные.

## Модули

- incoming.py — завершённый однократный опыт без offset; сохраняет приватный
  временный журнал. Не является постоянным вторым хранилищем.
- inbox.py — серверный репозиторий, один пакет входящих и доставка ответа.
- inbox_worker.py — явный запуск ограниченного числа пакетов, максимум 100.
- inbox_routes.py — список обращений, переписка, подготовка/подтверждение ответа,
  отмена ещё не отправленного текста, ручная сверка спорной доставки.
- inbox.sql — пять таблиц: потребитель/курсор, события, диалоги, сообщения,
  попытки ответа; индексы/ограничения, серверные RPC, RLS, клиентские права закрыты.

## До рабочей установки

1. Принять локальный результат, сохранить исходники коммитом и синхронизировать
   через GitHub Desktop. Зафиксировать SHA. Код не запускает DDL при старте.
2. Отдельно согласовать схему, целевую базу, резервное сохранение и миграцию.
   SQL проверяется на временной PostgreSQL 16.15; целевая версия — 17.
3. Определить срок хранения персональных данных и правила удаления/переноса.
   В events хранится полный полученный пакет для разбора неизвестных типов и
   проверки дублей; автоматическая очистка пока не реализована. Минимизировать
   срок хранения исходных событий перед постоянной эксплуатацией. Имена/телефоны
   в интерфейсе не используются; тексты и идентификаторы не пишутся в общие логи.
4. Владелец отдельно разрешает перенос двух событий временного опыта или выбирает
   новые сообщения. Этот код сам временный SQLite не читает и не удаляет.
5. После установки оператор вызывает cf_inbox_configure с проверенными bot_id,
   channel_id и chat_id служебного DM-чата. Начальный next_offset=NULL: первая
   загрузка читает ранние неподтверждённые события, не пропуская их вручную.

## Включение — только по согласованию

CF_INBOX_UI_ENABLED=1 открывает чтение/подготовку ответов в /studio/cccp/inbox.
Без флага страница показывает, что возможность ещё не подключена, не читая БД.

CF_INBOX_RECEIVE_ENABLED=1 разрешает операторский запуск inbox_worker.py.
Команда дополнительно требует --confirm-offsets: получение **может подтверждать**
ранее сохранённые события, в отличие от первого опыта.

Из CF-application после конкретного разрешения владельца:

    .venv/bin/python inbox_worker.py --bot-id ID --confirm-offsets --batches 1

ID заменяется на проверенный ID бота. Бот/DM-чат/webhook проверяются до чтения;
webhook не переключается. allowed_updates не задаётся, старый фильтр не меняется.
Один запрос timeout=20; это ограниченное получение, не вечный фоновый процесс.
При любой ошибке дальнейшие пакеты не запрашиваются. В stdout только количество
и курсор. Не использовать отладочные сетевые логи с токенами.

CF_INBOX_REPLY_ENABLED=1 и CF_INBOX_ALLOWED_REPLY_IDS (UUID конкретных ответов
через запятую) разрешают только отдельно просмотренные ответы. Без обоих условий
send_reply отказывает до БД/сети. Текст адресата не вводится в форму: маршрут
получается из сохранённого события, с direct_messages_topic_id, не message_thread_id.
Включение этих параметров не меняет CF_PUBLICATION_* и не разрешает публикации.

## Как сохраняются события

Один потребитель получает блокировку строки бота в БД. Другой процесс отклоняется.
Блокировка не истекает автоматически: после аварии нужна остановка прежнего
процесса и явный cf_inbox_recover_consumer(bot_id,true,основание), решение сохраняется.
Чужой/внешний потребитель Telegram должен быть исключён владельцем отдельно.

Весь пакет и распознанные сообщения сохраняются одной транзакцией, затем в той
же транзакции сохраняется следующий offset. Лишь следующий сетевой запрос может
подтвердить этот диапазон Telegram. После сбоя пакет приходит повторно: уникальный
bot_id/update_id и идентификатор сообщения защищают от дублей. Неизвестный тип
сохранён как unsupported, но не превращается в текстовое обращение.
Статус диалога new сбрасывается при новом входящем. Кнопка «Обработано» проверяет,
что после отображения страницы не пришло ещё одно сообщение.

## Как отправляется ответ

Подготовка сохраняет неизменяемый текст с UUID формы, без отправки. Исправление —
отмена prepared и подготовка нового ответа. На подтверждении видны текст ответа,
диалог и последнее обращение. Отправка отдельно подтверждается владельцем.

RPC атомарно переводит prepared → sending до единственного POST sendMessage.
Успех проверяет бота, чат, DM-тему и message_id; receipt сохраняется в sent.
Повторный claim невозможен. Ответ не помечает диалог обработанным автоматически.

Если сеть/БД не подтвердили результат — needs_review или оставшийся sending,
который оператор переводит на проверку. Не нажимать отправку заново.
После остановки отправителя сверить Telegram: вручную подтвердить найденное
сообщение либо засвидетельствовать отсутствие доставки и закрыть попытку.
Сохранённые сообщения не удалять, к прямому отправителю не возвращаться.

## Проверка перед подключением

Из CF-application:

    .venv/bin/python -m unittest discover -s tests -v

Полные SQL-тесты используют только кластер, описанный в sql/README.md:

    CF_TEST_POSTGRES=1 .venv/bin/python -m unittest discover -s tests -v

Адрес, имя БД и data_directory проверяются до сброса синтетических таблиц.
SQL-тесты не используют .env/SUPABASE_URL. Постоянного получателя, публичного
доступа, вложений/редактирований, автоматических ответов ИИ этот этап не создаёт.
Вложения/неизвестные события сохраняются для последующего разбора без имитации
успешной обработки. UI остаётся локальным и однопользовательским.
