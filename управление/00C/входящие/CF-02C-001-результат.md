Владелец фиксирует краткий протокол без значений секретов:

| Проверка | Что записать | Условие продолжения |
|---|---|---|
| Рабочая папка | Абсолютный путь, откуда сейчас запускается приложение, нет ли другой активной копии | Однозначно определён оригинал |
| Состав | Относительные пути исходников, шаблонов, статики, тестов, вспомогательных скриптов; скрытые файлы; символические ссылки | Нет пропущенных рабочих ресурсов и зависимостей вне папки |

| Запуск | Версия Python, используемое окружение, рабочая директория, точная команда, модуль и объект FastAPI | Воспроизводимый локальный запуск |

Список установленных пакетов перед публикацией просмотреть: в нём могут оказаться приватные URL. Не запускать неизвестные скрипты ради инвентаризации.

## 3. Безопасная последовательность

### Шаг 1 — зафиксировать исходное состояние и резервную копию

После согласования определить оригинал и сохранить открытые изменения редактора. Зафиксировать состояние Git, если он есть. На время копирования остановить процессы, которые пишут локальные файлы, либо обеспечить согласованный снимок.

Создать датированную копию всей рабочей папки **вне любого репозитория и облачной публикации**, включая скрытые файлы. Секреты в резервной копии остаются приватными и защищаются как оригинал. Проверить открытие копии, наличие ключевых файлов и совпадение состава/размеров; для важных исходников — контрольных сумм. Копия .venv не заменяет воспроизводимый список зависимостей.

**Контроль:** записаны путь копии, время и результат проверки. Оригинал не перемещён и остаётся точкой возврата. Этот снимок не является резервной копией внешней БД.

### Шаг 2 — выбрать способ объединения

Если исходная папка не связана с нужным origin, предпочтительный путь: через GitHub Desktop клонировать **существующий** MikKrak/ChannelFactory в новую отдельную папку. Проверить origin, main, актуальный commit и наличие документации. Не использовать Publish repository, не инициализировать поверх оригинала новую историю и не применять force push.

Если .git уже есть, сначала проверить origin и историю. При другом репозитории, вложенной истории или незакоммиченных изменениях остановить объединение и представить 00C конкретное состояние. Не выполнять reset, clean, автоматическое слияние несвязанных историй или удаление .git.

### Шаг 3 — подготовить исключения и список разрешённых файлов

В новом клоне создать рабочую ветку от актуальной main. До копирования подготовить/дополнить существующий .gitignore, сохранив его правила. Предлагаемые исключения: .env и его локальные варианты, .venv/venv, __pycache__, *.pyc, .DS_Store, журналы, кэш, приватные выгрузки, локальные БД и резервные копии. Точные пути исключений определить по инвентаризации; нужные шаблоны и статику не исключать вслепую.

Файл-пример конфигурации допустим только с именами и пустыми/очевидно фиктивными значениями; если исключается .env.*, явно разрешить выбранный .env.example. .gitignore не удаляет уже отслеживаемые секреты: отдельно проверить отслеживаемые файлы и историю, если локальный Git существует.

Скопировать в CF-application/ **только проверенный перечень** исходников и ресурсов. Не копировать исходную папку целиком, .git, .env или .venv. Не менять документацию корня и не перестраивать модули заодно с переносом.

**Контроль перед коммитом и повторно перед Push:** список всех изменённых/новых файлов, просмотр полного diff, локальная проверка секретов с результатом без значений. Если обнаружен настоящий секрет в истории, не публиковать; отдельно согласовать отзыв/замену и очистку. Одного удаления строки недостаточно.

### Шаг 4 — проверить новую локальную копию

Создать отдельное окружение в новом клоне, установить проверенные зависимости; оригинальную .venv не изменять. Приватную конфигурацию разместить только локально и убедиться, что она игнорируется. Перед запуском проверить побочные действия при импорте и старте.

Запускать из документированной директории по фактически найденному модулю. Команда `uvicorn main:app --reload` применима лишь если подтверждены main.py, объект app и соответствующая рабочая директория.

Сначала проверить отсутствие ошибок импортов, затем загрузку шаблонов и статики, открытие /, /materials, /posts и существующих карточек. Сравнить с исходным прототипом. Чтение выполнять после проверки, что маршруты не имеют скрытых операций записи.

Изменения черновика и переходы статусов — только на согласованных тестовых данных. Публикацию в действующий Telegram-канал не использовать как автоматический smoke-тест: она требует явного подтверждения. Не запускать одновременно два polling-процесса или автоисполнителя. Не регистрировать webhook при проверке переноса.

**Контроль:** таблица «сценарий / результат / ошибка», команда запуска и версии. При ошибке остановить новую копию и вернуться к оригиналу; не исправлять оригинал ради соответствия переносу. Изменения внешних данных откатываются отдельно, возврат папки их не отменяет.

### Шаг 5 — проверить GitHub Desktop и обмен

В Desktop убедиться, что выбраны нужный клон и рабочая ветка. После проверки состава сделать коммит и Push ветки; предложить PR в main с перечнем файлов и результатами локальных проверок. Слияние — по согласованию через 00C.

Для проверки GitHub → Mac использовать небольшое согласованное изменение несекретной документации: сначала проверить отсутствие незакоммиченных изменений, затем Fetch/Pull нужной ветки и сверить commit/содержимое. Для Mac → GitHub — обратное небольшое изменение, Commit/Push, чтение результата через GitHub-плагин. При конфликте сохранить обе версии и разобрать diff; не выбирать массово «заменить всё».

Оригинал и резервную копию сохранять до подтверждения запуска из нового клона и обоих направлений обмена. Постоянный рабочий путь назначить явно; оригинал не удалять автоматически.

## 4. Будущая структура и Vercel

Предлагаемая схема, **не фактическое дерево и не приказ создать файлы сейчас**:

```text
MikKrak/ChannelFactory/
├── INDEX.md, AGENTS.md, STATUS.md, PROJECT_RULES.md и существующая документация
└── CF-application/
    ├── <проверенные Python-модули с сохранённой внутренней структурой>
    ├── <реальные шаблоны и статические ресурсы>
    ├── <проверенный manifest зависимостей и при необходимости lock-файл>
    ├── <инструкция локального запуска>
    └── <при необходимости пример конфигурации без секретов>
```

Не выбирать сейчас между плоскими модулями и пакетом app/. Сначала сохранить рабочую структуру, затем отдельно согласовывать изменения импортов. В инструкции точно указать рабочую директорию, точку входа и поиск ресурсов.

Для будущего Vercel-проекта Root Directory = `CF-application`, относительно корня репозитория. Зависимости и точка входа должны разрешаться из выбранного корня; случайные зависимости от родительских папок исключить. По текущей документации Vercel FastAPI обнаруживается по объекту app в поддерживаемой точке входа; нестандартный модуль можно задать отдельно. Конкретный способ выбрать после чтения исходников. Не создавать заранее фиктивный main.py или универсальный vercel.json.

До отдельного согласования развёртывания требуется проверить:
- совместимость версии Python, библиотек, шаблонов и статики;
- лимиты времени, памяти, размера запроса/ответа и пакета для выбранного тарифа; численные лимиты перепроверить перед запуском;
- отсутствие постоянного polling, бесконечных циклов и длительного Engine внутри веб-функции; Engine остаётся на Mac по принятому плану;
- отсутствие зависимости от постоянного локального диска и памяти одного процесса;
- переменные окружения отдельно для тестового развёртывания, без передачи значений в GitHub;
- серверную защиту редакторских маршрутов и действий записи/публикации, включая прямые запросы; одного скрытия кнопок недостаточно;
- отсутствие отправок в действующий канал и изменений рабочих данных при старте/сборке;
- соответствие назначения проекта условиям Hobby.

Не подключать Vercel к репозиторию до этой проверки: импорт может запустить развёртывание. Webhook — следующий самостоятельный этап, с отдельной проверкой доставки и маршрутизации, а не часть миграции файлов.

Официальные источники, сверены 14.10.2026:
- [FastAPI on Vercel](https://vercel.com/docs/frameworks/backend/fastapi) — точки входа и модель запуска.
- [Build configuration](https://vercel.com/docs/builds/configure-a-build) — Root Directory.
- [Function limits](https://vercel.com/docs/functions/limitations) — ограничения выполнения.
- [Fair use](https://vercel.com/docs/limits/fair-use-guidelines) — Hobby для личного некоммерческого использования.
Перед фактическим развёртыванием повторить сверку.
