## 3. Предлагаемая схема поведения

1. Сервер получает post_id и ожидаемую revision с экрана подтверждения, читает готовый пост, строит неизменяемый план частей. Для фото заранее скачивает байты, проверяет формат и вычисляет SHA-256; URL и хеш сохраняются в плане, байты держатся для этого запуска. Не перегружать фото по изменившемуся URL в середине попытки.
2. Начало через RPC в одной транзакции блокирует строку cf_posts FOR UPDATE, проверяет ready/revision и отсутствие прежней попытки этой версии/неразобранной попытки любого номера. Одновременно сохраняет снимок и все части. Во время сетевой отправки транзакция не удерживается.
3. Порядок детерминированный: фото с подписью, если весь текст помещается; иначе фото, затем текстовые части по порядку. Склейка текста/источника и разбиение живут в одной чистой функции с номером алгоритма telegram-plain-v1. Номер части устойчив; ID бота, канал, метод, точный текст/подпись, URL/хеш фото фиксируются. Без parse_mode; лимиты проверять с консервативным подсчётом UTF-16, без разрыва Unicode-символа.
4. Перед КАЖДЫМ запросом отдельный RPC переводит pending → in_flight, проверив token владельца запуска, sending, срок и подтверждение всех предыдущих частей. Неоднозначный ответ самого RPC не даёт права отправлять: остановиться и сверять. Повтор claim никогда не возвращает новое разрешение для in_flight/confirmed.
5. После успешного ответа Telegram сразу записать chat_id/message_id/date данной части в отдельной короткой транзакции; лишь затем брать следующую. Повтор записи ТОГО ЖЕ результата идемпотентен; противоречащий ID — ошибка и проверка. Повтор сетевого запроса ради повторной записи запрещён.
6. Только когда все части confirmed, финальная транзакция ставит попытке succeeded, посту published и published_at = max(telegram_date) с сохранением точного снимка версии. Финализацию можно повторить как операцию БД без повторного Telegram-запроса.
7. Любая частичная отправка, тайм-аут, неоднозначность, отказ БД после отправки или обрыв процесса → needs_review/«Требуется проверка». Если БД недоступна, состояние может остаться sending; после восстановления его нельзя считать разрешением начать заново.
8. Для зависания review_after — сигнал остановки/проверки, НЕ срок автоматического освобождения блокировки. После перезапуска нет автоматического подхвата отправки даже если остались pending. Сервер переводит просроченную sending в needs_review, но не вызывает Telegram.
9. Сверка человеком не отправляет ничего: сначала остановить/дождаться прежнего worker и исключить поздний запрос, затем сопоставить части с каналом, внести доказанные ID/date, автора/время/причину решения. Поздний подтверждённый ответ прежнего worker можно ДОЗАПИСАТЬ, но нельзя продолжать следующую часть. Если все части подтверждены — финализация; если доказано, что не доставлена НИ ОДНА, cancelled_no_delivery. Наличие хотя бы одной доставки или неизвестного результата не позволяет просто снять запрет и отправить весь пост.
10. Для нового запуска после доказанной полной недоставки — явный возврат в draft и повторное утверждение с новой revision. Повтор прежней версии не разрешается. Для частичной публикации — отдельное решение, не автоматическое продолжение этого этапа. Абсолютную exactly-once доставку между БД и Telegram не обещаем.

Это конкретный объём двух таблиц, ограничений, защиты версии и атомарного начала. Статусы cf_posts не расширяются. SQL НЕ миграция к немедленному запуску: полные служебные RPC и защиты строк реализуются следующим заданием и сначала проходят изолированную проверку.

```sql
-- ПРОЕКТ, НЕ ПРИМЕНЁН. Итоговую миграцию сначала проверить в изолированной БД.
begin;

alter table public.cf_posts
  add column revision bigint not null default 1 check (revision > 0);

create table public.cf_publication_attempts (
  id uuid primary key, -- UUID запроса; формируется до начала RPC
  post_id uuid not null references public.cf_posts(id) on delete restrict,
  post_revision bigint not null check (post_revision > 0),
  bot_id bigint not null,
  chat_id bigint not null,
  snapshot jsonb not null check (jsonb_typeof(snapshot) = 'object'),
  plan_version text not null default 'telegram-plain-v1',
  state text not null default 'sending'
    check (state in ('sending','needs_review','succeeded','cancelled_no_delivery')),
  worker_token uuid not null,
  started_at timestamptz not null default now(),
  review_after timestamptz not null default (now() + interval '5 minutes'),
  finished_at timestamptz,
  reason_code text,
  review_note text,
  reviewed_by text,
  reviewed_at timestamptz,
  unique (post_id, post_revision),
  unique (id, chat_id)
);
-- Неразобранная попытка блокирует и новую редакцию того же поста.
create unique index cf_publication_one_unresolved
  on public.cf_publication_attempts(post_id)
  where state in ('sending','needs_review');

create table public.cf_publication_parts (
  attempt_id uuid not null,
  ordinal integer not null check (ordinal > 0),
  chat_id bigint not null,
  method text not null check (method in ('sendPhoto','sendMessage')),
  payload jsonb not null check (jsonb_typeof(payload) = 'object'),
  state text not null default 'pending'
    check (state in ('pending','in_flight','confirmed','rejected','unknown')),
  request_started_at timestamptz,
  message_id bigint check (message_id > 0),
  telegram_date timestamptz,
  recorded_at timestamptz,
  confirmation_source text check (confirmation_source in ('api','manual')),
  reason_code text,
  primary key (attempt_id, ordinal),
  foreign key (attempt_id, chat_id)
    references public.cf_publication_attempts(id, chat_id) on delete restrict,
  check (
    (state = 'confirmed' and message_id is not null
      and telegram_date is not null and recorded_at is not null
      and confirmation_source is not null)
    or
    (state <> 'confirmed' and message_id is null
      and telegram_date is null and recorded_at is null
      and confirmation_source is null)
  )
);
create unique index cf_publication_message_unique
  on public.cf_publication_parts(chat_id, message_id)
  where message_id is not null;

alter table public.cf_publication_attempts enable row level security;
alter table public.cf_publication_parts enable row level security;
revoke all on public.cf_publication_attempts, public.cf_publication_parts
  from public, anon, authenticated;
grant select, insert, update
  on public.cf_publication_attempts, public.cf_publication_parts to service_role;
-- Политик для браузера нет; ключ service_role остаётся только в Python.
-- DELETE не выдаётся: история результата не должна исчезать при обычной работе.

create function public.cf_guard_post_revision()
returns trigger language plpgsql security invoker set search_path = ''
as $f$
declare
  changed boolean;
begin
  if TG_OP = 'INSERT' then
    if NEW.status <> 'draft' or NEW.published_at is not null then
      raise exception 'New posts must start as unpublished drafts';
    end if;
    NEW.revision := 1;
    return NEW;
  end if;

  changed := NEW.title is distinct from OLD.title
    or NEW.blocks is distinct from OLD.blocks
    or NEW.material_id is distinct from OLD.material_id;

  if OLD.status = 'published'
     and (changed or NEW.status <> OLD.status
          or NEW.published_at is distinct from OLD.published_at) then
    raise exception 'Published post is immutable; create a new post';
  end if;

  if changed and (OLD.status <> 'draft' or NEW.status <> 'draft') then
    raise exception 'Return post to draft before editing';
  end if;

  if exists (
    select 1 from public.cf_publication_attempts a
    where a.post_id = OLD.id and a.state in ('sending','needs_review')
  ) and (changed or NEW.status <> OLD.status
         or NEW.published_at is distinct from OLD.published_at) then
    raise exception 'Publication attempt requires completion or review';
  end if;

  NEW.revision := OLD.revision +
    case when changed or (OLD.status = 'draft' and NEW.status = 'ready')
      then 1 else 0 end;

  if NEW.status = 'published' and OLD.status <> 'published' then
    if NEW.published_at is null or not exists (
      select 1 from public.cf_publication_attempts a
      where a.post_id = OLD.id and a.post_revision = OLD.revision
        and a.state = 'succeeded'
        and exists (select 1 from public.cf_publication_parts x where x.attempt_id=a.id)
        and not exists (
          select 1 from public.cf_publication_parts x
          where x.attempt_id=a.id and x.state <> 'confirmed'
        )
    ) then
      raise exception 'Publication receipts are incomplete';
    end if;
  elsif NEW.published_at is distinct from OLD.published_at then
    raise exception 'Published time is set only at successful completion';
  end if;
  return NEW;
end;
$f$;
create trigger cf_posts_revision_guard
  before insert or update on public.cf_posts
  for each row execute function public.cf_guard_post_revision();

-- Начало: короткая транзакция; сетевых вызовов внутри RPC нет.
create function public.cf_begin_publication(
  p_attempt_id uuid, p_worker_token uuid, p_post_id uuid,
  p_expected_revision bigint, p_bot_id bigint, p_chat_id bigint,
  p_parts jsonb
) returns uuid
language plpgsql security invoker set search_path = ''
as $f$
declare
  p public.cf_posts%rowtype;
  part jsonb;
  n integer := 0;
begin
  select * into p from public.cf_posts where id=p_post_id for update;
  if not found then raise exception 'Post not found'; end if;
  if p.status <> 'ready' or p.revision <> p_expected_revision then
    raise exception 'Post is not ready or revision has changed';
  end if;
  if exists (
    select 1 from public.cf_publication_attempts a
    where a.post_id=p.id
      and (a.post_revision=p.revision or a.state in ('sending','needs_review'))
  ) then raise exception 'Publication already started; inspect existing attempt'; end if;
  if jsonb_typeof(p_parts) is distinct from 'array'
     or jsonb_array_length(p_parts) not between 1 and 100 then
    raise exception 'Invalid publication plan';
  end if;

  insert into public.cf_publication_attempts
    (id,post_id,post_revision,bot_id,chat_id,snapshot,worker_token)
  values (p_attempt_id,p.id,p.revision,p_bot_id,p_chat_id,
    jsonb_build_object('title',p.title,'blocks',p.blocks,'material_id',p.material_id),
    p_worker_token);

  for part in select value from jsonb_array_elements(p_parts) loop
    if jsonb_typeof(part) is distinct from 'object'
       or coalesce(part->>'method','') not in ('sendPhoto','sendMessage')
       or jsonb_typeof(part->'payload') is distinct from 'object' then
      raise exception 'Invalid publication part';
    end if;
    n := n + 1;
    insert into public.cf_publication_parts
      (attempt_id,ordinal,chat_id,method,payload)
    values (p_attempt_id,n,p_chat_id,part->>'method',part->'payload');
  end loop;
  return p_attempt_id;
end;
$f$;
revoke all on function public.cf_begin_publication(uuid,uuid,uuid,bigint,bigint,bigint,jsonb)
  from public, anon, authenticated;
grant execute on function public.cf_begin_publication(uuid,uuid,uuid,bigint,bigint,bigint,jsonb)
  to service_role;
revoke all on function public.cf_guard_post_revision() from public, anon, authenticated;
grant execute on function public.cf_guard_post_revision() to service_role;

-- В ИТОГОВОЙ миграции обязательны также RPC, описанные в таблице ниже,
-- и защита неизменности снимка, плана и подтверждённых результатов.
-- Без них включать отправку нельзя; этот DDL — предложение объёма, не релиз.
commit;
```

### Обязательные RPC и ограничения следующего задания

Все RPC — SECURITY INVOKER, SET search_path='', квалифицированные таблицы; EXECUTE отозвать у PUBLIC/anon/authenticated, выдать только service_role. Порядок блокировок всегда: cf_posts → attempt → part, чтобы избежать взаимных блокировок.

| Операция | Точная обязанность |
| --- | --- |
| cf_claim_publication_part(attempt UUID, worker UUID, ordinal INT) → payload | Блокировки указанного порядка; state=sending, срок не истёк; предыдущие номера confirmed; текущая pending. UPDATE in_flight + request_started_at=clock_timestamp(), RETURNING. Ноль строк/ошибка/неопределённость → сетевой вызов запрещён. |
| cf_record_publication_part(attempt UUID, worker UUID, ordinal INT, chat BIGINT, message BIGINT, telegram_date TIMESTAMPTZ) | Проверить token, канал и in_flight; записать confirmed/date/message/source=api. В needs_review принимать только поздний результат ранее начатой части. Повтор идентичных полей возвращает успех без изменения; другой результат отклоняет. Продолжать sending можно только после этой записи. |
| cf_review_publication(attempt UUID, reason TEXT) | Только sending → needs_review; код причины из белого списка, без сырого URL/токена. Не сбрасывать in_flight/pending и не менять снимок. Просроченная попытка не получает нового worker/token. |
| cf_finish_publication(attempt UUID) | Заблокировать post/attempt; проверить количество частей и отсутствие не-confirmed; допустим sending либо полностью разобранная needs_review. В одной транзакции attempt succeeded и post published/время. Повтор после succeeded сверяет и возвращает прежний результат. |
| cf_reconcile_publication(...) | Только ручное решение владельца после прекращения старого sender. Сохраняет reviewer/time/note и доказанные receipts с source=manual. Не вызывает отправку. cancelled_no_delivery только без confirmed и при явном доказательстве отсутствия всех доставок; один лишь тайм-аут таким доказательством не является. |

Триггеры на новых таблицах дополнительно запрещают изменение attempt.post_id/post_revision/bot_id/chat_id/snapshot/plan_version/worker_token после вставки, изменение состава/номеров/method/payload частей после создания, удаление попыток/частей и перезапись подтверждённых receipts. Переходы состояний ограничить перечисленными контрактами; в том числе needs_review не возвращается в sending. Нельзя выдавать RPC через SECURITY DEFINER в обход отсутствующей политики. Сервисный ключ — доверенный серверный доступ, он не заменяет защиту редактора перед публичным запуском.

Старый cf_posts_set_updated_at остаётся; revision от него независима и повышается только при изменении содержания или новом утверждении draft → ready. Смена статуса доставки сама по себе не создаёт новую версию. Исторические записи не объявляются опубликованными задним числом и не получают вымышленные receipts. Старые опубликованные записи показывать как «данные отправки не зафиксированы».

Приведённый guard проверяет попытки из коротких транзакций; cf_finish сначала меняет attempt, затем post внутри той же транзакции. До полного набора RPC/триггеров отправка должна оставаться выключенной. SQL синтаксически и конкурентно в отдельной PostgreSQL ещё НЕ испытан — это обязательная часть реализации, не подтверждённый результат этого задания.

## 5. Локальные правки следующего задания

- Новый publication.py: чистая сборка плана и оркестратор RPC → одна часть Telegram → запись результата; никаких сетевых автоповторов.
- telegram.py: разделить подготовку фото и отправку одной уже подготовленной части; возвращать нормализованный receipt. Не создавать requests-сессию с автоматическими retries отправки. Передавать фактический MIME изображения вместо постоянного image/jpeg.
- database.py: отдельные обёртки RPC и чтение состояния; включить revision в чтение. Получать UUID черновика непосредственно из cf_save_material_draft, а не считать ответ RPC объектом поста.
- main.py: старый publish-now и экран подтверждения используют тот же publication.py; запрет отправки не-ready и изменившейся revision обязателен. Убрать обход прямым publish_to_telegram.
- studio.py/studio_views.py: подтверждение отправки готового поста с revision; отображение прогресса «k из n», sending/needs_review, IDs и опубликованного времени; при ошибке блокируется повтор отправки, но доступна сверка без сетевого действия. Возврат к редактированию запрещён при неразобранной попытке.
- Новые тесты publication и SQL-интеграции. Обычную блокировку кнопки оставить только как удобство, не как гарантию.
- requirements.txt и зависимости по умолчанию не менять; входящие таблицы и обработчики не добавлять.

## 6. Проверка и возврат

| Проверка без рабочих данных | Ожидаемый результат |
| --- | --- |
| draft/published/устаревшая revision | До обращения к Telegram отказ; записей отправки нет |
| Два параллельных начала одной версии | Ровно одна попытка/план, второй запрос получает существующее состояние; проверка на настоящей изолированной PostgreSQL двумя соединениями |
| Одновременное редактирование и начало | Один из запросов ждёт строковую блокировку и затем проверяет новую revision/status; снимок не расходится |
| Фото + длинный текст | Устойчивый порядок; следующая часть лишь после подтверждения записи предыдущей |
| Полный успех и повтор финализации | Все receipts сохранены, published/время ровно от этой попытки, сетевой повтор отсутствует |
| Успех первой части, отказ второй | Первая остаётся confirmed; needs_review; весь пост не published, автопродолжения нет |
| Доставка, затем падение до записи / ответ RPC потерян | Неопределённость видна; ни новый процесс, ни повтор формы не отправляет заново |
| Отказ БД до claim/после claim/после receipt | До подтверждённого claim сети нет; дальше остановка, доступна только сверка и идемпотентная дозапись результата |
| Перезапуск и просроченная sending | needs_review, без освобождения версии и без нового сетевого действия |
| Прямой старый publish-now | Те же проверки и журнал, что у нового кабинета |
| Поздний ответ worker после needs_review | Сохраняется известный receipt, следующая часть не отправляется |
| Смена снимка/плана/чужой token/противоречащий ID | Отказ БД; подтверждённая история неизменна |
| Повтор manual reconcile/cancel | Только прежний согласованный результат; подтверждённые части не теряются |

Миграцию сначала проверить на одноразовой PostgreSQL с копией ТОЛЬКО структуры cf_* и синтетическими данными. Сначала выключить все отправители; затем одна транзакция DDL, проверка прав/RLS/ограничений, тесты параллелизма. При ошибке до COMMIT — ROLLBACK, запуск старой отправки не считать разрешённым автоматически.

После реальных отправок нельзя откатить программу на старый путь без журнала: он снова создаст дубли. Безопасный возврат — отключить отправку, оставить чтение кабинета и журналы/receipts. Удаление новой схемы/данных допустимо только до реальных отправок и после отдельного решения, без CASCADE на чужие объекты. Откат кода не удаляет сообщения из канала.

Опыт с рабочей базой и Telegram — отдельно: выбрать material_id/post_id с владельцем, согласовать текст/изображение и канал, записать исходные значения и допустимые операции draft/ready/published. Пока IDs не утверждены. Создание/сохранение через новый кабинет проверить сначала на согласованном тестовом материале; этим заданием ни запись, ни публикация не выполнялись.

## 7. Пробелы и необходимые решения

1. Принять контрольный снимок кабинета и дать владельцу точку commit/Pull/Push; два локальных экземпляра перед будущей миграцией остановить согласованно.
2. Утвердить две таблицы, revision, перечисленные RPC/триггеры и серверный service_role-доступ без публичных политик. Не смешивать с исправлением чужих таблиц общего Supabase-проекта.
3. Утвердить правило неопределённости и ручной проверки: нет автоповторов и таймерного «разблокирования». Если частичная отправка остаётся неразобранной, исходный пост заморожен.
4. Назначить отдельное задание реализации и изолированную PostgreSQL для проверки миграции. SQL в этом отчёте не заменяет тестируемую миграцию.
5. Отдельно согласовать реальную запись и тестовую отправку с конкретными IDs. Разрешение на обследование не является разрешением на отправку.
6. Внешние потребители Telegram неизвестны. Отсутствие webhook позволяет рассматривать polling позже, но не утверждает и не запускает его.
7. Общие STATUS и планы ещё содержат устаревшие этапы. Здесь изменяются только план 02C, отчёт и статус CF-02C-006; навигатор исключён.
