# 02C → 00C: локальная реализация надёжной публикации

Дата: 29.10.2026.
Основание: принятое обследование [CF-02C-006](CF-02C-006-результат.md) и прямое разрешение владельца «Ты можешь начинать разработку, приступай». Отдельного задания CF-02C-007 на момент начала не было; номер задания не присваивался.

## Результат

Реализация выполнена **локально** в CF-application/ на Mac. Базовый HEAD: 2b0e59c1d7f3ad41236e11d98e642f258dd5a97c. Нового коммита исходников нет; синхронизацию через GitHub Desktop выполняет владелец. Ранее незакоммиченные изменения кабинета сохранены.

- publication.py: единый сервис публикации, проверка версии готового поста, последовательная отправка частей, сохранение подтверждений, остановка при неопределённом результате без автоматического повтора.
- telegram.py: транспорт с одной сетевой попыткой, проверкой ответа и изображения; прежний прямой отправитель отключён в новом коде. Реальная отправка по умолчанию закрыта: нужны CF_PUBLICATION_ENABLED=1 и явный список CF_PUBLICATION_ALLOWED_POST_IDS.
- publication_routes.py: общие маршруты старого редактора и Studio, подтверждение публикации, журнал частей, ручная сверка спорных результатов без повторной отправки.
- sql/publication.sql: revision, таблицы cf_publication_attempts/cf_publication_parts, ограничения/триггеры/RPC, атомарный захват, фиксация результата, защита от конкуренции и журнал ручных решений. Это SQL-скрипт; в рабочую Supabase он не применялся и зарегистрированной миграцией не является.
- main.py подключает общий сервис; studio.py/studio_views.py показывают журнал. Исправлена передача ID созданного черновика.
- sql/README.md: порядок последующего подключения и проверки, ограничения, команды изолированных тестов.
- tests/: проверки сервиса, маршрутов и реальной SQL-логики в отдельной временной базе.

## Проверки

35 тестов прошли. Проверены конкурирующие старты, порядок частей, потерянный ответ, сбой записи после доставки, перезапуск, истечение срока, повторная фиксация подтверждения, ручная сверка, запреты изменения журнала напрямую, Unicode и совпадение планов Python/SQL. Проверен полный цикл реального Python-репозитория через именованные SQL RPC с тестовым транспортом.

Исправлен найденный дефект SQL-защиты: сохранение исправленного черновика и переход в ready одним обновлением теперь разрешены и покрыты тестом. Проверка git diff --check успешна.

SQL испытан на локальной PostgreSQL 16.15; рабочий проект использует PostgreSQL 17. Применение и проверка на целевой версии остаются отдельной контрольной точкой. Использовалась только временная база cf_publication_test с синтетическими данными, без TCP. После тестов временный сервер остановлен. Сценарий сброса тестовой схемы защищён проверками имени базы и точного каталога временного кластера.

## Границы результата

Рабочая Supabase, секреты/.env, настройки бота и реальные сообщения не изменялись. Приложение для проверки этой реализации не запускалось; браузерная проверка нового блока публикации ещё не проводилась. Проверки интерфейсных маршрутов выполнены изолированно.

Найденные ранее работающие экземпляры приложения не останавливались. Они могут сохранять прежний прямой отправитель в памяти: изменение исходников их не обновляет. До будущего подключения необходимо согласованно остановить старые экземпляры и запускать проверенную версию.

Приём обращений читателей, polling/webhook, навигатор, production и Vercel не выполнялись. Абсолютная однократная доставка между Telegram и БД не обещается; неопределённость требует ручной сверки, а не повторного запуска.

## Следующее решение

Просьба принять локальный результат и согласовать контрольный коммит/синхронизацию, остановку старых экземпляров, применение SQL и выбранный тестовый post_id. После этого отдельно проверить сохранение/ready и одну реальную публикацию с журналом. Исторический draft/ready не доказывает отсутствие прежней отправки — выбранный пост нужно сверить с каналом.

До этого включение отправки и изменения рабочей базы не выполняются.
