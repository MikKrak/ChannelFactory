## Риски, найденные в коде

1. В main.py нет проверки владельца перед чтением редакторских страниц и POST-действиями. Открыты /import, /material/{id}/load, /material/{id}/save-post, /post/{id}/save и /post/{id}/publish-now. Последний маршрут можно вызвать напрямую, минуя экран подтверждения.
2. publish-now отклоняет published, но не требует ready; результат Telegram не сохраняется в базе. Повторная отправка остаётся риском. В первом серверном испытании предлагается вообще не выдавать приложению рабочий Telegram-токен.
3. database.py создаёт клиент при импорте и требует SUPABASE_URL и SUPABASE_KEY. На отдельной тестовой базе нужны не только таблицы cf_materials/cf_posts, но и RPC-функция cf_save_material_draft, ограничения и права. Их определения в восьми файлах отсутствуют; перенос схемы нельзя угадывать.
4. static и templates/index.html ищутся относительно рабочей директории. Локальный запуск из CF-application подтверждён; доступность ресурсов в серверной сборке ещё проверить.
5. В прочитанном коде нет постоянного worker/polling или webhook. Операции HTTP к источнику и Telegram выполняются синхронно и могут быть длительными; их тайм-ауты не гарантируют укладывание полного запроса в лимит Vercel.
6. Ветки разделяют исходники, но не данные. Preview из main с тем же Supabase-ключом может менять те же записи, что сервер из production. Ключ сервера не является авторизацией человека, открывшего редактор.

## Следующие действия — по порядку

### 1. Зависимости и воспроизводимый запуск

После разрешения на этот шаг получить из работающей .venv только имена и версии пакетов, без .env и секретов. По импортам и запуску нужны восемь прямых зависимостей:

`fastapi`, `uvicorn`, `requests`, `feedparser`, `beautifulsoup4`, `supabase`, `python-dotenv`, `python-multipart`.

python-multipart нужен для FastAPI Form; отдельный пакет telegram не нужен — импортируется собственный telegram.py. Jinja2 текущая загрузка HTML не использует.

Подготовить CF-application/requirements.txt с точными **фактически работающими** версиями. Для воспроизводимости сохранить проверенные версии нужных транзитивных зависимостей; не считать восемь строк с закреплёнными прямыми пакетами полным закреплением окружения. Не копировать весь список разработки без проверки, особенно приватные URL и локальные пути.

Установить зависимости в отдельное чистое окружение Python 3.12, сохранив работающую .venv. Проверить согласованность пакетов и запуск из CF-application командой python -m uvicorn main:app. Успешный запуск и необходимые сценарии на согласованных тестовых данных записать вместе с commit SHA. Не обновлять библиотеки до последних версий одновременно с первым воспроизводимым запуском.

Vercel поддерживает requirements.txt и Python 3.12; фактическая patch-версия сервера может отличаться от локальной 3.12.1. Версию Python для проекта закрепить отдельно согласованным способом. [Документация Python runtime](https://vercel.com/docs/functions/runtimes/python).

**Готово, когда:** установка в чистом окружении воспроизводится и приложение запускается без изменения старого окружения.

### 2. Обмен GitHub Desktop в обе стороны

Проверить origin MikKrak/ChannelFactory, выбранную main и незакоммиченные изменения; при конфликте сохранить обе версии и разобрать его без force/reset.

GitHub → Mac: использовать этот отчёт как уже разрешённое изменение документации, выполнить Fetch/Pull и проверить путь, текст и коммит. Mac → GitHub: после согласования внести небольшую запись о проверке в существующий рабочий документ, сделать Commit/Push main; 02C повторно читает файл через плагин и сверяет коммит. Не создавать новую ветку ради этой проверки.

**Готово, когда:** подтверждены оба направления и совпадение файлов; перед следующим запуском отдельно проверена загрузка актуального кода сервером.

### 3. Защита редактора и политика Preview — до первого открытого запуска

Согласовать простую серверную проверку доступа одного владельца, без регистрации посторонних и новой многопользовательской системы. Реализация — отдельное разрешённое изменение main, затем проверка на Mac. Закрыть редакторские GET-страницы и все перечисленные POST-маршруты; при cookie/session-доступе предусмотреть защиту от поддельных запросов из чужого сайта (CSRF). Ошибки не должны показывать токены и адреса запросов, содержащие токен.

Проверка без авторизации: прямые GET и POST должны отклоняться до обращения к базе или Telegram. С авторизацией: чтение и изменение разрешённых тестовых данных работают. В Vercel отдельно проверить стандартный домен, адрес конкретного deployment и Preview, если он разрешён.

Deployment Protection Vercel может быть дополнительным барьером; его область действия надо проверить. Standard Protection не закрывает production-домены, а Password Protection недоступна на Hobby. Это не основание оставлять серверные действия без проверки владельца. [Deployment Protection](https://vercel.com/docs/deployment-protection).

**Предложение для первого этапа:** отключить автоматические Preview из main. Если 00C выберет Preview, ему нужны отдельная безопасная конфигурация/тестовые данные и та же защита доступа; рабочие ключи и Telegram-токен не наследовать автоматически.

### 4. Подготовить проверенную версию и создать production

После шагов 1–3 зафиксировать конкретный commit main, результаты Mac и состав изменений. Получить разрешение владельца **на этот SHA**, затем создать production от него. Если main успела измениться, не брать новый HEAD автоматически: проверить изменения и согласовать новую версию.

В дальнейшем сравнивать production с одобренным состоянием main, показывать состав выпуска через PR или сравнение коммитов. Не подключать автоматическое слияние main → production. Если после проверки main появились новые изменения, переносить только одобренное состояние; проверять итоговый код после слияния. Сохранить предыдущий SHA/deployment для возврата. Откат кода не откатывает изменения базы.

**Готово, когда:** production действительно указывает на одобренную версию; это проверено чтением GitHub.

### 5. Настроить Vercel и проверить разделение

После отдельного разрешения на настройку/первый deployment: проект ChannelFactory, репозиторий MikKrak/ChannelFactory, Root Directory = CF-application, точка входа main.py:app. По текущей документации такая точка входа поддерживается; не переносить модули ради новой структуры и не задавать Uvicorn --reload как команду серверного запуска. Проверить зависимости, шаблон и CSS. [FastAPI on Vercel](https://vercel.com/docs/frameworks/backend/fastapi).

**Production Branch = production.** По документации настройка находится в Project Settings → Environments → Production → Branch Tracking. По умолчанию Vercel выбирает main; другие ветки могут создавать Preview. [Git deployments](https://vercel.com/docs/git).

При импорте нельзя считать первый автоматический deployment уже настроенным выпуском: до подключения рабочих данных проверить выбранную ветку и защиту. Если интерфейс сначала создаёт deployment и лишь затем позволяет изменить Branch Tracking, использовать только предварительно защищённый проверенный код без рабочих ключей; такой запуск не принимать как готовую серверную версию. После настройки выпустить одобренный SHA production.

Для отключения автоматических deployment других веток после согласования можно использовать CF-application/vercel.json, параметр git.deploymentEnabled: шаблон "*" = false и "production" = true. По текущей документации совпадающее правило true разрешает production; неуказанные ветки без общего запрета разрешены по умолчанию. Проверить поведение фактически. Конфигурация должна быть и в main, иначе её deployment может остаться разрешённым. [Git configuration](https://vercel.com/docs/project-configuration/git-configuration).

Проверка разделения после разрешения: записать SHA и ID действующего production-deployment; сделать разрешённое небольшое изменение main, убедиться, что production и его домен не обновились, а Preview соответствует выбранной политике. Проверить также PR-события. Ручной deployment/promote из main не использовать как обход решения владельца. Отдельно одобренный выпуск production должен обновить сервер именно до ожидаемой версии.

### 6. Проверить Supabase с сервера

До выдачи переменных окружения выбрать с 00C тестовый проект или конкретный материал/черновик в существующей базе и допустимые изменения. Разделение веток не создаёт отдельную базу.

Передать SUPABASE_URL/SUPABASE_KEY через серверные настройки Vercel для нужного окружения, не в GitHub и не в HTML. Определить тип ключа без публикации значения. Secret/service_role обходит RLS — ограничения доступа к строкам; он не заменяет проверку владельца в FastAPI. Проверить права таблиц, правила RLS и RPC; не включать публичную запись и не менять схему ради устранения ошибки без разрешения. [Supabase API keys](https://supabase.com/docs/guides/getting-started/api-keys).

Из защищённого серверного интерфейса:
1. Открыть материалы и посты, затем карточку выбранного тестового материала.
2. Создать/обновить только согласованный черновик через cf_save_material_draft.
3. Сохранить изменённый текст; отдельным чтением убедиться, что база содержит ожидаемые текст и статус.
4. При согласовании проверить draft → ready; для возврата/очистки заранее определить разрешённый способ, не придумывать несуществующий маршрут.
5. Проверить отсутствие изменения рабочих записей и отправки в Telegram. Ошибки записать без секретов.

Импорт RSS не использовать как первый тест записи: /import делает upsert и может затронуть существующие материалы. На новой базе сначала отдельно проверить требуемую схему и RPC. Changelog Supabase предупреждает об изменении автоматического доступа новых таблиц через Data API: при создании тестовой базы проверить явные разрешения, а не копировать предположения старого проекта. [Изменение Data API](https://supabase.com/changelog/45329-breaking-change-tables-not-exposed-to-data-and-graphql-api-automatically).

**Готово, когда:** зафиксированы deployment/SHA, среда базы, тестовые IDs, результат записи и отдельного чтения, а также отсутствие доступа без авторизации. Затем передать факты 00C для STATUS. Telegram webhook и публикация — отдельные последующие задания.
