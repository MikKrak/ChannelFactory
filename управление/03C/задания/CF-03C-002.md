# CF-03C-002 — Локальный HTML-просмотр Markdown

**От:** 00C — Управление ChannelFactory  
**Кому:** 03C — Исследования  
**Дата:** 15.10.2026  
**Статус:** IN_PROGRESS

## Цель

Провести минимальный технический эксперимент: Markdown-файл в локальной папке проекта отображается браузером как HTML через локальный сервер. После изменения исходного Markdown и ручного обновления страницы видна новая редакция. Это предварительная проверка технологии для возможного применения в другом крупном проекте; универсальный просмотрщик не разрабатывать.

## Контекст и полномочия

Прочитать AGENTS.md, PROJECT_RULES.md, STATUS.md, собственный план и протокол вертикального обмена. Работать в существующей локальной папке ChannelFactory, предварительно проверив путь и состояние файлов.

Этим заданием отдельно разрешён небольшой экспериментальный код в изолированной области проекта вне CF-application/. Прежде чем создавать файлы, сообщить владельцу точный путь, состав изменений и способ запуска. Работа в описанных границах согласована; повторное разрешение на каждый файл не требуется. Новые зависимости и выход за границы задания согласовать отдельно.

Рабочие документы проекта остаются в GitHub. Markdown-файлы эксперимента — локальные синтетические образцы, а не новые канонические документы ChannelFactory. Код приложения, действующие документы и окружение приложения не менять.

## Этап 1 — подготовка и первый просмотр

1. Создать отдельную небольшую экспериментальную область, например experiments/markdown-preview/, после проверки отсутствия чужих файлов по этому пути. Не перезаписывать существующие материалы.
2. Создать два коротких Markdown-файла с вымышленным содержимым. В основном показать несколько уровней заголовков, текст, списки, таблицу, внутренние ссылки и ссылку на второй Markdown-файл; во втором — обратную ссылку. Небольшое оглавление и переходы по заголовкам желательны, если почти не усложняют решение.
3. Выбрать простейшее преобразование Markdown в HTML с корректными таблицами. Проверить доступные средства без чтения секретов. Не устанавливать большие комплексы и не менять рабочую .venv приложения. Если требуется небольшая библиотека, сначала согласовать её установку в отдельное окружение эксперимента; не устанавливать без подтверждения.
4. При каждом HTTP-запросе читать актуальный Markdown и преобразовывать его в HTML. Markdown остаётся единственным источником содержимого; постоянную независимую HTML-копию не создавать. Для эксперимента отключить кеширование ответов.
5. Запустить сервер на свободном порту с привязкой только к 127.0.0.1. Не использовать 0.0.0.0, внешний туннель, публикацию или доступ из локальной сети. Действующий сервер приложения не останавливать и не перенастраивать.
6. Сервер должен отдавать только специально выбранные файлы экспериментальной области. Запретить выход за неё через относительные пути, URL-кодирование и символические ссылки; не открывать корень проекта и не включать произвольную выдачу файлов. Не выдавать .env, .git, виртуальные окружения или реальные документы проекта. Избегать внешних скриптов, шрифтов и других сетевых ресурсов; не добавлять исполнение пользовательского HTML/JavaScript из Markdown.
7. Проверить ответ страницы: HTML, корректная кодировка, таблицы и переходы между Markdown-страницами, якоря заголовков. Дать владельцу адрес вида http://127.0.0.1:PORT/... . По возможности один раз открыть в доступной браузерной панели.
8. Предложить владельцу проверить, что он видит оформленную HTML-страницу, а не исходный Markdown или HTML-код.

**Контрольная точка:** остановиться и дождаться подтверждения владельца, что первая страница открылась правильно. Задание остаётся IN_PROGRESS. До подтверждения не менять содержимое ради этапа 2.

## Этап 2 — изменение источника и обновление страницы

После подтверждения первого просмотра:
1. Изменить исходный Markdown: добавить хорошо заметную новую редакцию текста и изменение в таблице.
2. Предложить владельцу вручную обновить ту же страницу.
3. Отдельным HTTP-чтением проверить наличие нового содержимого. Не подменять эту проверку регенерацией статической HTML-копии.
4. Попросить владельца подтвердить, что новая редакция видна в браузере. Успех пользовательского сценария фиксировать только после его подтверждения; технические проверки описать отдельно.

## Ограничения

- Не публиковать документы и файлы проекта в интернете.
- Не менять архитектуру ChannelFactory, CF-application/, рабочую .venv, зависимости приложения, данные, настройки GitHub, Vercel, Supabase или Telegram.
- Не делать commit/push локальных экспериментальных файлов: синхронизацию выполняет владелец через GitHub Desktop.
- Не разрабатывать автоматическое обновление браузера, HTML-редактор Markdown, поиск, индексацию или универсальный просмотрщик.
- Не менять другие файлы без необходимости; документацию эксперимента держать в его области, отчёт — в 00C.
- Если инструмент или среда блокирует локальный запуск, указать точную причину и доступный безопасный следующий шаг, не объявлять запуск успешным.
- В отчёте указать, как остановить именно этот экспериментальный сервер, не затрагивая другие процессы.

## Критерий успеха

Владелец открывает локальную HTML-страницу рядом с чатом и после изменения Markdown и ручного обновления видит новую редакцию. Таблица и ссылки отображаются корректно; сервер читает Markdown при запросе и не выдаёт файлы за пределами экспериментальной области.
