# AGENTS.md — инструкция для помощников ChannelFactory

## Постоянный контекст

- **Проект:** ChannelFactory — универсальная no-code/AI-assisted фабрика контентных каналов и тематических сообществ.
- **Канонический GitHub-репозиторий:** `MikKrak/ChannelFactory` — https://github.com/MikKrak/ChannelFactory
- **Основная ветка:** `main`.
- **Текущий эксперимент:** Telegram-канал «СССР — Свой Сад Своими Руками», бот `@cccp_service_bot`; рабочее приложение Python/FastAPI, Supabase, Telegram Bot API.
- **Локальная разработка:** macOS, VS Code, проектная папка `ChannelFactory`, виртуальное окружение `.venv`. Абсолютный путь и состояние локальных файлов нельзя предполагать без проверки.
- **Предпочтение общения:** русский язык, на «ты»; конкретные объяснения, небольшие проверяемые шаги, не перегружать инструкциями.

## Организация работы

- **GitHub — через подключённый плагин напрямую.** Для чтения и записи в `MikKrak/ChannelFactory` переход в Work не требуется. Не предлагать Work вместо доступной операции GitHub.
- **Управляющий чат:** `00C — Управление ChannelFactory`; специализированные чаты — `01C — Концепция` и `02C — Разработка`. Карта ролей: `управление/структура-чатов.md`.
- **Вертикальный обмен:** задания от 00C вниз, результаты и вопросы вверх; порядок в `управление/иерархический-обмен.md`. Чаты не активируют друг друга автоматически. Исполнитель при запуске сам берёт первое невыполненное задание из своей папки по правилам протокола; владелец не передаёт номера заданий.
- **Согласованное имя программного каталога:** `CF-application/`. В каталоге находятся исходники перенесённой и проверенной на Mac программы. Для Vercel планируется Root Directory `CF-application`; развёртывание не выполнено.
- **Каноническая навигация:** `INDEX.md`; организационные правила: `PROJECT_RULES.md`; организационный план: `управление/план-проекта.md`. Не создавать конкурирующие копии решений.
- Изменения структуры и кода выполнять в согласованных границах; локальный Mac и секреты не трогать без отдельного согласования.

## Старт каждой новой сессии

1. **Не искать название репозитория заново:** для этой работы использовать `MikKrak/ChannelFactory` как известный адрес. Проверять доступность через GitHub-коннектор; поиск репозитория нужен только при реальной ошибке доступа или явном указании другого проекта.
2. Прочитать `INDEX.md`, `PROJECT_RULES.md`, `AGENTS.md` и **`STATUS.md`** из `main`, чтобы установить правила, текущую фазу и подтверждённые результаты.
3. По задаче читать `концепция/CONCEPT.md` (развивающаяся концепция и архитектурные принципы), `разработка/DEVELOPMENT.md` (решения, исследования и гипотезы), `reference/PLAN.md` (план и история), `README.md` (назначение и навигация), `docs/NOTEBOOK_PROTOCOL.md` (только при работе с Блокнотом).
4. Учитывать текущий разговор: он может содержать более свежие результаты, чем GitHub. При расхождении **не выдавать старый STATUS за актуальный**; проверить и предложить синхронизацию.
5. Для операций в GitHub **использовать подключённый GitHub-плагин** и точный адрес `MikKrak/ChannelFactory`. Для чтения конкретного файла — `fetch_file`, для правки — `update_file` с проверенным SHA; новый файл — `create_file`. Не подменять запись в репозиторий текстом в чате.
6. Не путать GitHub и локальный Mac: изменения в GitHub **не обновляют автоматически** локальные файлы VS Code. Исходники уже находятся в GitHub; локальная копия может отставать до Fetch/Pull. Не утверждать, что локальный код изменён, если изменён только GitHub.

## Карта документов

- `INDEX.md` — индекс и навигация по репозиторию.
- `PROJECT_RULES.md` — общие организационные правила и полномочия.
- `управление/структура-чатов.md` — роли специализированных чатов.
- `управление/иерархический-обмен.md` — протокол заданий и результатов.
- `управление/план-проекта.md` — организационный план, без дублирования технического.
- `разработка/WORK_PLAN.md` — архивная ссылка, не действующий план.
- `AGENTS.md` — это руководство и постоянный адрес проекта.
- `STATUS.md` — только **проверенное** состояние реализации и ближайший эксперимент; обновлять после подтверждённых результатов.
- `концепция/CONCEPT.md` — основное место для согласованных принципов и развивающейся концепции продукта; отличать принятые направления от открытых решений.
- `разработка/DEVELOPMENT.md` — технические исследования, эксперименты, альтернативы и рабочие заметки; явно отделять факты от гипотез.
- `reference/PLAN.md` — этапы, расходы, история опытов; не считать старые «следующие шаги» текущими без сверки со STATUS.
- `README.md` — назначение, архитектурные принципы и вход в документацию.
- `docs/NOTEBOOK_PROTOCOL.md` — правила синхронизации редактируемых Блокнотов, если этот режим явно используется.

- Основные локальные модули по последним сведениям: `main.py`, `database.py`, `telegram.py`, `source.py`, `extractor.py`, `editor.py`; БД Supabase `cf_materials`, `cf_posts`. Проверять фактическое состояние перед изменением кода.

## Правила работы

- Перед записью читать актуальную версию целевого файла, сохранять остальное содержимое и избегать дублирования.
- В сообщении о выполнении указывать **путь, ссылку и commit SHA**. Не говорить «записал», если GitHub не подтвердил запись.
- Не создавать дубликаты задач и документов, когда нужный файл уже существует.
- Секреты (`TELEGRAM_BOT_TOKEN`, `SUPABASE_KEY`, `.env`) не печатать, не цитировать и не сохранять в GitHub.
- Новые возможности Telegram, тарифы и API считать гипотезами до проверки по официальной документации и эксперименту. Не смешивать `getUpdates` с обработкой события приложением.
- При согласовании продуктовых и архитектурных принципов обновлять `концепция/CONCEPT.md`; технические исследования вести в `разработка/DEVELOPMENT.md`; подтверждённые результаты — в `STATUS.md`. Не смешивать концепцию, факт и план.
- Прямой запрос пользователя «запиши в Development/репозиторий» означает **реальную запись в GitHub**, а не предложение перейти в другой режим.

## Актуальный цикл и планы

`main` — разработка и проверка на Mac; `production` — будущая ветка одобренной версии для Vercel. Защита редактора нужна до публичного запуска, сейчас не выполняется. Один короткий общий план: `управление/план-проекта.md`; отдельные планы — `управление/00C/план.md`, `управление/01C/план.md`, `управление/02C/план.md`. `разработка/WORK_PLAN.md` не действующий план. Планы писать кратко и предметно, подробности — в заданиях.
